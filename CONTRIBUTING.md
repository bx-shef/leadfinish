# Правила работы с репозиторием

## Язык

Общаемся, пишем документацию, описания PR и комментарии в коде — **на русском**.

## Ветки

- **В `main` напрямую не пушим никогда.**
- Вся работа ведётся в отдельной ветке, изменения вносятся через Pull Request.
- Имя ветки — по смыслу задачи: `feat/lock-screen`, `fix/money-nbsp`,
  `docs/module-structure`.

```bash
git checkout main && git pull origin main
git checkout -b feat/lock-screen
git push -u origin feat/lock-screen
```

## Защита `main`

Ветка защищена ruleset'ом, так что правила выше — не только договорённость:

- прямой пуш в `main` невозможен, только через PR;
- требуемая проверка одна — **`CI`**. `PHP 8.x` и `Build` — её зависимости, в
  настройках они не перечисляются, поэтому новая задача попадает под защиту
  сама собой;
- ветка PR должна быть свежей относительно `main` — если `main` уехал вперёд,
  GitHub предложит кнопку **Update branch**;
- незакрытые обсуждения в PR держат мерж;
- мерж только **Squash**;
- апрувов требуется **0**. Не потому что ревью не нужно, а потому что в
  репозитории один человек: свой PR апрувить нельзя, и единица заперла бы
  репозиторий наглухо.

⚠ Переименуете задачу в `ci.yml` — поправьте и ruleset. Проверки сопоставляются
по имени, строкой: требование к исчезнувшему имени не выполнится никогда, и
PR встанет намертво.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <что сделано, в повелительном наклонении, с маленькой буквы>

<тело: зачем это нужно и на что влияет>
```

Типы: `feat` — новое поведение, `fix` — исправление, `docs` — документация,
`chore` — служебное (версии, сборка, зависимости), `refactor` — правка без
изменения поведения, `test` — тесты.

Примеры из жизни:

```
feat(lock): приостановка доработки до оформления приёмки

Расписание в .settings.php, две ступени: soft — напоминание с отсчётом,
hard — подбор не открывается. Hard запрещается в контроллере, а не только
на фронте.
```

```
fix(search): раскрывать HTML-сущности в сумме сделки

CCrmCurrency::MoneyToString() делает strip_tags, но &nbsp; оставляет,
и фронт рисовал сущность текстом.
```

Правила заголовка:
- до ~70 символов, без точки в конце;
- **что сделано, а не что происходило**: «добавить проверку прав», не «добавил»
  и не «правки»;
- область в скобках — по модулю или подсистеме, если это что-то проясняет;
- `BREAKING CHANGE:` в теле, если ломается совместимость — нужно, чтобы потом
  собрать Changelog.

Тело нужно там, где из заголовка не видно **зачем**. Однострочный `chore` тела не
требует.

## Pull Request

- Описание пишем текстом **прямо в теле PR**: что изменено, почему, на что
  влияет. Репозиторий приватный — внешних ссылок на задачи может не быть.
- **Одна логическая задача — один PR.** Не мешаем несвязанные правки: PR из двух
  тем невозможно ни нормально отревьюить, ни откатить.
- Если по ходу нашлось постороннее — заводим issue, а не дописываем в этот PR.

Тело PR по структуре:

```markdown
## Что сделано
…

## Зачем
…

## На что влияет
… (совместимость, миграции, необходимость переустановки модуля)

## Как проверить
1. …
```

## Проверка перед мержем

1. Забрать изменения из `main` и убедиться, что **нет конфликтов**.
2. **CI зелёный.** Красный CI — не повод мержить «потом починим». Требуемая
   проверка одна — `CI`; `PHP 8.1/8.2/8.3` и `Build` — её зависимости.
3. Синтаксис: `php -l` по всем PHP, `node --check` по JS — локально это
   `./build.sh --check`, то же самое делает CI.
4. Пройден приёмочный сценарий из `CLAUDE.md` модуля.
5. Поднята версия в `install/version.php`, если менялось поведение.
6. Документация (`README.md`, `CLAUDE.md`, `docs/`) не отстаёт от кода.
7. Закрыты **все** вопросы ревью. Не «учту» — либо исправлено, либо отвечено,
   почему не исправляется.
8. Секреты в диффе отсутствуют: токены, вебхуки, пароли. Реальные значения
   живут в `.env` (в `.gitignore`), в репозиторий попадает только `.env.example`.

## Слияние

- **Мержит всегда владелец репозитория сам.** Автомерж и принудительный мерж не
  используем.
- Тип слияния — **Squash and Merge**.
- Сообщение сквоша — это и есть запись в истории: заголовок по Conventional
  Commits, в теле — что менялось. Если были `BREAKING CHANGE`, они должны
  оказаться именно здесь, иначе Changelog потом не собрать.
- PR не мержится, пока не получен явный сигнал от владельца.

## После мержа

- Предложить удалить влитую ветку.
- Если менялось поведение — выпустить релиз: **Actions → Release → Run workflow**
  от `main` (тег поставится сам из `install/version.php`) либо тегом `vX.Y.Z`
  с рабочей машины. CI соберёт релиз с приложенной поставкой.
- Синхронно обновить `docs/` — документация не должна отставать от реального
  состояния.
- Follow-up задачи завести как issue с хорошим контекстом: что именно, почему не
  вошло в PR, где смотреть.
- Если PR закрыл issue — закрыть issue.

## Тесты

Тесты пишем **по мере написания кода**, а не потом. Нетривиальную чистую логику —
маппинги, разбор дат, матрицы переходов, нормализацию — покрываем в том же PR и
гоняем в CI.

Живут в `tests/` в корне репозитория, по файлу на тему, имя вида `*_test.php`.
Запускаются как `php tests/имя_test.php`, все сразу — через `./build.sh --check`.
Ядро Битрикса подменяется заглушками прямо в тесте, чтобы проверялся настоящий
класс, а не его копия. В поставку `tests/` не попадает: архив собирается из
каталога модуля.

То, что завязано на рантайм Битрикса, покрывается приёмочным чек-листом из
`CLAUDE.md`. Это осознанный компромисс, а не отсутствие проверки: чек-лист
обязателен к прохождению перед мержем.
