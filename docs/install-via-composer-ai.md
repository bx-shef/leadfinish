# Установка через Composer — для AI-ассистента

Инструкция для агента, который ставит модуль на портал сам. Человеческий вариант
— `install-via-composer.md`; дублировать его здесь не надо, здесь то, что
ассистент обычно делает не так.

Главное правило: **проверяй, а не предполагай**. Почти каждый шаг ниже
заканчивается измерением, потому что все перечисленные ошибки выглядят как
успешные.

⚠ Схема действует **с версии 1.7.0**. До неё модуль ставился в `local/modules/` и
требовал `installer-paths`. Убедись, какая версия ставится, прежде чем применять
что-либо отсюда: `composer show bxshef/leadfinish`.

## Что выяснить до первой команды

Не начинай, пока не ответил на всё это фактами из системы, а не из общих знаний.

| Вопрос | Как узнать |
| --- | --- |
| Где docroot портала | конфиг vhost; наличие `bitrix/` и `local/` рядом |
| Есть ли уже `composer.json` и **где именно** | `find <docroot> -maxdepth 2 -name composer.json` |
| Установлен ли модуль сейчас | `ModuleManager::isModuleInstalled('shef.leadfinish')` |
| Где лежат файлы модуля | `ls -a <docroot>/bitrix/modules/shef.leadfinish` и то же в `local/modules` |
| Под кем работает php-fpm | `ps -o user= -C php-fpm \| sort -u` |
| Открыт ли `vendor/` из веба | запрос к `/vendor/autoload.php`, см. раздел про безопасность |

Если модуль уже стоит — сначала пойми, **как** он поставлен и **какой версии**.
Архивом и Composer'ом одновременно держать один каталог нельзя.

## Порядок

### 1. Снять прежнюю установку, если она была

Снимай **через админку** — Marketplace → Установленные решения → «Удалить», и
обязательно **до** удаления файлов: установщик лежит в каталоге модуля.

⚠ Не вызывай `ModuleManager::unRegisterModule()` из консоли. Он только снимает
отметку: обработчик события останется в `b_module_to_module` и будет падать на
каждой странице, а каталог `/bitrix/js/shef.leadfinish/` — висеть без хозяина.
Симметрично и на установке: `registerModule()` не делает ни регистрации событий,
ни копирования фронта.

Проверить: `isModuleInstalled` = `false`, в `b_module_to_module` нет строк с
`TO_MODULE_ID='shef.leadfinish'`, каталог `/bitrix/js/shef.leadfinish/` исчез.

Только после этого удалять каталог модуля.

⚠ Обратный порядок оставит запись в базе о модуле, которого нет, обработчик
события, который будет падать, и каталог ассетов, который уже никто не уберёт.

### 2. Проверить, где лежит `composer.json`

**Самая тихая ошибка этой схемы.** Пакет ставится в
`{bitrix_dir}/modules/shef.leadfinish/`, где `bitrix_dir` по умолчанию — `bitrix`
относительно каталога с `composer.json`.

Измерено:

| `composer.json` | Результат |
| --- | --- |
| корень портала | `bitrix/modules/shef.leadfinish/` ✔ |
| `<docroot>/local/` | `local/bitrix/modules/shef.leadfinish/` ✘, **без предупреждений** |

Если файл не в корне портала — либо перенеси его, либо задай путь явно:

```json
"extra": { "bitrix-dir": "../bitrix" }
```

Проверено: с этой строкой из `/local/` модуль встаёт правильно.

Если `composer.json` уже существует — **правь его, а не перезаписывай**.
Перезапись снесёт чужие зависимости, и узнают об этом не сразу.

### 3. Разрешить плагин и установить

```json
"config": { "allow-plugins": { "composer/installers": true } }
```

```bash
cd <каталог с composer.json> && composer require bxshef/leadfinish:^1.7
```

Без разрешения Composer 2 **обрывает установку с ошибкой** — это единственное
место схемы, где отказ громкий сам по себе. Остальное проверяй руками.

### 4. Проверить раскладку — четырьмя измерениями

Ни одно из них не заменяется чтением вывода `composer`.

```bash
# 1. каталог назван по ID модуля и лежит в корне портала
test -d <docroot>/bitrix/modules/shef.leadfinish && echo ok

# 2. .settings.php на месте — ls без -a его НЕ покажет
test -f <docroot>/bitrix/modules/shef.leadfinish/.settings.php && echo ok

# 3. не уехало ли в local/bitrix — признак ошибки из шага 2
test -d <docroot>/local/bitrix && echo ПЛОХО

# 4. версия соответствует ожидаемой
grep VERSION <docroot>/bitrix/modules/shef.leadfinish/install/version.php
```

Проверка 2 — не формальность. `.settings.php` содержит ajax-контроллеры и список
доступа; без него модуль ставится, грузится и **не работает**, а причина не видна.

### 5. Зарегистрировать модуль

Composer этого не делает. **На этом шаге фронт копируется в `/bitrix/js/`** —
пропустив его, получишь модуль без интерфейса.

Ставить **через админку**: Marketplace → Установленные решения → «Установить».

⚠ Из консоли не ставь. `ModuleManager::registerModule()` лишь помечает модуль
установленным — обработчик события не регистрируется, фронт не копируется, и
модуль будет числиться рабочим, ничего не делая. Если доступа к админке нет —
это блокер задачи, а не повод обойти установку скриптом: сообщи и остановись.

Проверить четырьмя измерениями:

```php
ModuleManager::isModuleInstalled('shef.leadfinish');     // true
Loader::includeModule('shef.leadfinish');                // true
class_exists('\Shef\LeadFinish\Controller\DealBinder');  // true
is_dir($docroot . '/bitrix/js/shef.leadfinish');         // true
```

Третье отдельно: автозагрузка ищет файл по имени класса **в нижнем регистре**, и
заглавная буква в `lib/` ломает модуль только на Linux.

И обработчик события:

```sql
SELECT TO_CLASS, TO_METHOD FROM b_module_to_module
WHERE TO_MODULE_ID = 'shef.leadfinish';
-- ожидается \Shef\LeadFinish\EventHandler::onEpilog
```

### 6. Проверить, что фронт отдаётся

Единственная проверка, которую нельзя заменить взглядом на файлы.

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  http://<портал>/bitrix/js/shef.leadfinish/js/lead-finish-button.js     # 200

curl -s -o /dev/null -w '%{http_code}\n' \
  http://<портал>/bitrix/modules/shef.leadfinish/js/lead-finish-button.js # 403
```

403 во второй строке — **правильный** результат, а не поломка. Каталог модуля
закрыт правилом nginx из поставки:

```nginx
location ~* ^/bitrix/(modules|local_cache|stack_cache|managed_cache|php_interface) {
    deny all;
}
```

Именно поэтому установка копирует фронт в `/bitrix/js/<ID>/`.

### 7. Заполнить список доступа

Строго **после** шага 3: раскладка файлов перетирает `.settings.php`.

В поставке `allowed_users => [1]`. Это рабочее значение, а не «пусто»: кнопку
увидит только администратор портала.

⚠ Пустой список означает **всех авторизованных**, а не «никого». Не используй его
как способ временно выключить доработку.

## Ловушки, на которых ассистент спотыкается чаще человека

**Вывод `composer` выглядит успешным всегда.** `Installing bxshef/leadfinish` он
напечатает и тогда, когда файлы уехали в `local/bitrix/modules/`. Единственный
признак — проверки 1 и 3 из шага 4.

**`ls` скрывает `.settings.php`.** Перечисление каталога без `-a` создаёт
убедительную картину полной установки без главного файла конфигурации. Я на этом
уже ошибался: увидел «всё на месте» в списке из десяти строк и чуть не записал
успех.

**Установка ≠ раскладка файлов.** До `DoInstall()` фронта в `/bitrix/js/` нет, и
модуль выглядит установленным, но не работает. Проверка — шаг 6.

**403 на каталоге модуля — норма.** Не «чини» это правилом nginx: оно защищает
исходники всех модулей портала, включая чужие.

**Фатальная ошибка в CLI-скрипте с прологом Битрикса не печатается.** Пролог
включает буферизацию вывода, и при падении буфер теряется — скрипт выглядит как
молча завершившийся. Если PHP-проверка не вывела ничего, это не «пусто», а скорее
всего падение: пиши результат в файл (`file_put_contents`) и читай его отдельно,
либо выполняй шаги по одному.

**Теги репозитория ≠ версии пакета.** На Packagist попадают только теги, в
которых `composer.json` существует и его `name` совпадает с именем пакета.
Проверяй доступное: `composer show bxshef/leadfinish --all`.

## Безопасность: проверь, открыт ли `vendor/`

В поставке BitrixVM правило закрыто комментарием, а соседнее создаёт обманчивую
картину защиты:

```nginx
#location ~* /vendor/ {
#    deny all;
#}

location ~* /composer {
    deny all;
}
```

Правило `/composer` ловит всё, где в пути есть это слово, поэтому `composer.json`,
`composer.lock` и содержимое `vendor/composer/` отдают 403. Легко решить, что
`vendor/` закрыт. Он не закрыт:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://<портал>/vendor/autoload.php
# 200 с пустым телом = PHP выполнил файл
```

Сам `autoload.php` безвреден. Риск появляется с первой зависимостью, у которой
есть исполняемый файл по пути без слова `composer`.

⚠ Правка конфигурации веб-сервера на чужом портале — действие, которое стоит
согласовать, а не выполнить молча. Сообщи о находке и предложи; молчать о ней
тоже нельзя.

## Чего не делать

- **Не смешивать способы установки.** Каталог ставится либо архивом, либо
  Composer'ом.
- **Не перезаписывать существующий `composer.json` портала.**
- **Не чинить `allowed_users => []` на «никому».** Пустой список означает «всем»,
  и это решение владельца, а не ошибка.
- **Не удалять каталог модуля до снятия регистрации** — иначе останется каталог
  ассетов в `/bitrix/js/`, который уже нечем убрать.
- **Не считать `composer require` установкой модуля.** Он раскладывает файлы.

## Итоговая проверка

Модуль установлен верно, если выполняется всё сразу:

1. `<docroot>/bitrix/modules/shef.leadfinish/.settings.php` существует;
2. каталога `<docroot>/local/bitrix/` не появилось;
3. `Loader::includeModule('shef.leadfinish') === true`;
4. `class_exists('\Shef\LeadFinish\Controller\DealBinder') === true`;
5. в `b_module_to_module` есть `\Shef\LeadFinish\EventHandler::onEpilog`;
6. `/bitrix/js/shef.leadfinish/js/lead-finish-button.js` отдаёт **200**;
7. `allowed_users` содержит нужные ID.

Приёмочный сценарий интерфейса — в `CLAUDE.md`, раздел «Проверка». Он не
заменяется списком выше: тот проверяет установку, а этот — что доработка работает.
