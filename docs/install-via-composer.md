# Установка через Composer — по шагам

Для человека, у которого есть доступ к серверу портала. Если Composer не нужен —
ставьте архивом из релиза, это проще и описано в `README.md`.

Проверено на коробочном Битрикс24 (BitrixVM-подобное окружение, nginx + php-fpm):
установка, регистрация модуля, отдача фронта и удаление выполнены целиком,
результаты ниже описаны по факту.

⚠ **Начиная с версии 1.7.0.** В прежних версиях модуль ставился в
`local/modules/` и требовал `installer-paths` в `composer.json` проекта. Если
Composer поставил вам версию ниже 1.7 — эта инструкция к ней не относится.
Указывайте `^1.7`.

## Коротко

```bash
cd /home/bitrix/www        # ВАЖНО: корень портала, см. шаг 1
composer require bxshef/leadfinish:^1.7
```

Путей настраивать не нужно. Дальше — регистрация модуля в админке и правка
списка доступа: **Composer только раскладывает файлы**.

## Шаг 1. Положить `composer.json` в корень портала

Это не вкусовщина, а требование схемы. Пакет ставится в
`{bitrix_dir}/modules/shef.leadfinish/`, где `bitrix_dir` по умолчанию — `bitrix`
**относительно каталога с `composer.json`**.

Измерено:

| Где `composer.json` | Куда ляжет модуль |
| --- | --- |
| `/home/bitrix/www/` — корень портала | `bitrix/modules/shef.leadfinish/` ✔ |
| `/home/bitrix/www/local/` | `local/bitrix/modules/shef.leadfinish/` ✘ |

Второй случай — бессмыслица, и происходит она **молча**: Composer отчитается об
успехе, а модуль не появится в списке решений.

Если `composer.json` всё-таки должен лежать в другом месте, путь к ядру задаётся
явно:

```json
"extra": { "bitrix-dir": "../bitrix" }
```

Проверено: с этой строкой из `/local/` модуль встаёт в `bitrix/modules/` портала
правильно.

## Шаг 2. Разрешить плагин раскладки

Единственное, что требуется в `composer.json` проекта:

```json
{
    "config": {
        "allow-plugins": { "composer/installers": true }
    }
}
```

Это требование самого Composer, а не модуля: без явного разрешения Composer 2 не
запускает плагины, а раскладыванием по путям занимается именно плагин.

Забыли — **установка обрывается с ошибкой**, в `vendor/` тоже ничего не остаётся.
Отказ громкий, тихой подмены пути не бывает.

## Шаг 3. Установить

```bash
cd /home/bitrix/www
composer require bxshef/leadfinish:^1.7
```

Проверить, что файлы там, где нужно:

```bash
ls -a /home/bitrix/www/bitrix/modules/shef.leadfinish/
```

Должны быть `.settings.php`, `include.php`, `install/`, `lib/`, `js/`, `css/`,
`lang/`. **`.settings.php` — с точки, обычный `ls` его не покажет**, а без него
модуль нерабочий: в нём и ajax-контроллеры, и список доступа.

Права: Composer кладёт файлы от того пользователя, под которым запущен. Если это
не `bitrix` — поправить:

```bash
chown -R bitrix:bitrix /home/bitrix/www/bitrix/modules/shef.leadfinish
```

## Шаг 4. Установить модуль в портале

Composer этот шаг не заменяет, и пропустить его нельзя: **на этом шаге фронт
попадает туда, откуда браузер его получит**.

Админка → **Marketplace → Установленные решения** → «[SH-local] Своя кнопка
завершения лида» → **Установить**.

⚠ **Только через админку.** `ModuleManager::registerModule()` из консоли лишь
помечает модуль установленным: обработчик события не регистрируется, фронт не
копируется. Модуль будет числиться установленным и ничего не делать.

Проверить:

```php
\Bitrix\Main\Loader::includeModule('shef.leadfinish');      // true
\Bitrix\Main\ModuleManager::getVersion('shef.leadfinish');  // 1.7.0
```

И что фронт отдаётся:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  http://<портал>/bitrix/js/shef.leadfinish/js/lead-finish-button.js
# 200
```

### Почему фронт переезжает

Каталог модуля браузеру недоступен. В поставке nginx:

```nginx
location ~* ^/bitrix/(modules|local_cache|stack_cache|managed_cache|php_interface) {
    deny all;
}
```

Измерено: `/bitrix/modules/shef.leadfinish/js/...` → **403**,
`/bitrix/js/shef.leadfinish/js/...` → **200**.

Поэтому установка копирует `js/` и `css/` в `/bitrix/js/shef.leadfinish/` — ровно
как это делают штатные модули Битрикса. Удаление модуля убирает **только** этот
подкаталог.

## Шаг 5. Вписать, кому показывать кнопку

**После** шага 3, не раньше: раскладка файлов перетирает `.settings.php`.

Открыть `/home/bitrix/www/bitrix/modules/shef.leadfinish/.settings.php` и
заменить список:

```php
'allowed_users' => [
    'value' => [44, 562],   // ID сотрудников
    'readonly' => false,
],
```

В поставке там `[1]` — только администратор портала. Пока список не поправлен,
менеджер кнопки не увидит, и выглядеть это будет как «модуль не работает».

⚠ Очистить список, чтобы «пока выключить», **нельзя**: пустой список значит
обратное — кнопка появится у всех авторизованных.

## Шаг 6. Сбросить кеш JS/CSS

Ctrl+F5 либо админка → «Настройки продукта» → «Автокеширование» → сбросить.

Путь вида `/bitrix/cache/js/s1/...` в консоли браузера означает, что смотрите на
кеш, а не на файлы модуля.

## Обновление

```bash
cd /home/bitrix/www
composer update bxshef/leadfinish
```

Затем **переустановить модуль** в админке, если обновлялся фронт: файлы в
`/bitrix/js/` обновляются установкой, а не распаковкой.

⚠ **Обновление перетирает `.settings.php`** — вместе со списком `allowed_users` и
расписанием приостановки. Выпишите значения до и верните после:

```bash
cat bitrix/modules/shef.leadfinish/.settings.php     # до
composer update bxshef/leadfinish
vim bitrix/modules/shef.leadfinish/.settings.php     # после
```

## Удаление

1. **Снять модуль через админку** — Marketplace → Установленные решения →
   «Удалить». Тем же действием убирается обработчик события и каталог
   `/bitrix/js/shef.leadfinish/`.
2. Убрать файлы:

   ```bash
   cd /home/bitrix/www
   composer remove bxshef/leadfinish
   ```

Порядок важен: сначала снять регистрацию, пока файлы установщика на месте. Она же
убирает фронт из `/bitrix/js/`. Удалив каталог первым, вы оставите и запись в
базе, и каталог с ассетами.

Привязки, сделанные модулем, **не откатываются**: `LEAD_ID` у сделок и статусы
лидов остаются как есть. Это обычные данные CRM.

## Безопасность: проверьте, открыт ли `vendor/`

В поставке BitrixVM правило закрыто комментарием, а соседнее создаёт обманчивую
картину защиты — `nginx/inc/block.conf`:

```nginx
#location ~* /vendor/ {
#    deny all;
#}

location ~* /composer {
    deny all;
}
```

Правило `/composer` ловит всё, где в пути есть это слово, поэтому `composer.json`,
`composer.lock` и содержимое `vendor/composer/` отдают 403. Легко решить, что
`vendor/` закрыт. Он не закрыт:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://<портал>/vendor/autoload.php
# 200 с пустым телом = PHP выполнил файл
```

Сам `autoload.php` безвреден. Риск появляется с первой зависимостью, у которой
есть исполняемый файл по пути без слова `composer`. Починка — раскомментировать
готовое правило и перечитать конфигурацию:

```bash
nginx -t && nginx -s reload
```

## Если что-то не так

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Модуля нет в списке решений, файлы в `local/bitrix/modules/...` | `composer.json` лежит не в корне портала | шаг 1 |
| Пакет лёг в `vendor/bxshef/leadfinish` | версия ниже 1.7 либо плагин не разрешён | `composer show bxshef/leadfinish`, шаг 2 |
| Модуль стоит, кнопки нет, в консоли 403 на js | модуль не установлен через админку — фронт не скопирован | шаг 4 |
| Модуль стоит, кнопки нет, ошибок нет | `allowed_users` не поправлен, там `[1]` | шаг 5 |
| Кнопка была и пропала после обновления | обновление вернуло поставочный `.settings.php` | вернуть свой список |
| Правки фронта не видны | кеш JS/CSS | шаг 6 |
