# Сборка архива и установка модуля

В `shef.leadfinish` всё описанное ниже собрано в `./build.sh` — он же гоняется в
CI. Команды здесь приведены целиком: скрипт можно не заводить, но знать, что
именно он делает и почему, нужно.

## Перед сборкой

Обязательный минимум — иначе на портал уедет то, что даже не парсится:

```bash
find . -name '*.php' -print0 | xargs -0 -n1 php -l   # синтаксис PHP
node --check js/*.js                                  # синтаксис JS
```

Поднять версию в `install/version.php` — при **каждом** изменении поведения:

```php
$arModuleVersion = [
	'VERSION' => '1.3.0',
	'VERSION_DATE' => '2026-09-16 12:00:00',
];
```

Версия — единственный способ понять, что стоит на портале. Не поднял — на
следующем разборе «почему не работает» будешь гадать.

Актуализировать `README.md`: описание процесса не должно отставать от кода.

## Сборка

Архив содержит **каталог модуля целиком**, а не его содержимое. Внутри zip первым
уровнем должен лежать `shef.leadfinish/` — иначе при распаковке файлы рассыплются
по `/local/modules/`.

⚠ В `shef.leadfinish` такого каталога в репозитории **нет**: файлы модуля лежат в
корне, потому что Composer разворачивает в целевой каталог корень пакета целиком.
Значит каталог для архива надо собрать, а не заархивировать готовый:

```bash
staging=$(mktemp -d)
mkdir "$staging/shef.leadfinish"
cp -R .settings.php include.php install lang lib js css \
      README.md CLAUDE.md LICENSE composer.json "$staging/shef.leadfinish/"

rm -f shef.leadfinish.zip
(cd "$staging" && zip -rq "$OLDPWD/shef.leadfinish.zip" shef.leadfinish)
rm -rf "$staging"

unzip -l shef.leadfinish.zip | head    # проверить первый уровень
```

Проверка глазами обязательна: список должен начинаться с
`shef.leadfinish/...`, а не с `install/...`.

Что **не кладём** в архив: `tests/`, `docs/`, `build.sh`, `CONTRIBUTING.md`,
`.github/`, `.git/`, `*.min.js`/`*.map`, редакторский мусор.

`./build.sh` делает это сам и вдобавок проверяет, что в корне не завелось
ничего, о чём не решено, куда оно едет: каждый элемент верхнего уровня обязан
быть перечислен либо в `SHIP`, либо в `KEEP`. Неизвестный роняет сборку — иначе
новый файл однажды уехал бы на портал молча.

## Установка через Composer

Альтернатива архиву. Пакет — `bxshef/leadfinish`, тип `bitrix-d7-module`.

Путей настраивать не нужно: пакет приезжает в `bitrix/modules/shef.leadfinish/`
сам. Достигается это двумя полями **в самом пакете**:

```json
"type": "bitrix-module",
"extra": { "installer-name": "shef.leadfinish" }
```

Почему именно так, если делаешь такой же модуль:

- шаблон пути у типа `bitrix-module` — `{$bitrix_dir}/modules/{$name}/`, без
  вендора в имени каталога. У более нового `bitrix-d7-module` шаблон
  `{$bitrix_dir}/modules/{$vendor}.{$name}/`, и каталог получился бы
  `bxshef.leadfinish` — Битрикс ищет строго по ID модуля и такой не найдёт;
- `extra.installer-name` читается **из пакета** и подменяет `{$name}`. Это
  единственная переменная шаблона, на которую пакет может повлиять;
- `{$bitrix_dir}` берётся только из **корневого** `composer.json`
  (`BitrixInstaller::inflectPackageVars()`), поэтому положить пакет в `local/`
  без настройки у потребителя нельзя. Отсюда и выбор `bitrix/modules/`.

От потребителя требуется одно — разрешить плагин раскладки:

```json
"config": { "allow-plugins": { "composer/installers": true } }
```

Это требование Composer, а не наше. Забыли — **установка обрывается с ошибкой**,
в `vendor/` тоже ничего не остаётся: отказ громкий.

```bash
composer require bxshef/leadfinish
```

Composer только раскладывает файлы: ставится модуль всё равно через
**Marketplace → Установленные решения**.

⚠ Не подменяй установку вызовом `ModuleManager::registerModule()`. Он помечает
модуль установленным, но не выполняет `DoInstall()`: события не регистрируются,
файлы установки не раскладываются. Модуль будет числиться рабочим и ничего не
делать.

Что уедет в пакет, решает `export-ignore` в `.gitattributes`: GitHub собирает
dist-архив через `git archive`, а тот его соблюдает. ⚠ Список обязан совпадать с
`KEEP` в `build.sh` — разойдутся, и на портал попадёт разное в зависимости от
способа установки.

## Релиз вместо пересылки архива

Собранный архив удобно держать не в переписке, а на постоянной ссылке: тег
`vX.Y.Z` от основной ветки — и сборка выкладывается релизом сама. В
`shef.leadfinish` это `.github/workflows/release.yml`.

Полезно иметь и второй вход — кнопку в интерфейсе CI, которая выводит тег из
версии модуля и ставит его сама. Тогда релиз не требует ни рабочей машины, ни
прав на пуш тегов: это разные права, и у того, кто выпускает релиз, вторых
может не быть.

Тег обязан совпадать с `VERSION` внутри модуля, иначе релиз не соберётся:
архив, версия которого врёт, хуже отсутствующего — именно по версии потом
определяют, что стоит на портале.

## Куда класть

```
/home/bitrix/www/bitrix/modules/shef.leadfinish/
```

`local/modules/` тоже годится — модуль работает из обоих мест.

⚠ **Каталог модуля браузеру недоступен в любом из них.** В поставке nginx:

```nginx
location ~* ^/bitrix/(modules|local_cache|stack_cache|managed_cache|php_interface) {
    deny all;
}
```

Запрос к `/bitrix/modules/shef.leadfinish/js/...` отдаёт **403**. Поэтому модуль
с фронтом обязан копировать JS и CSS туда, откуда они отдаются, — в
`/bitrix/js/<ID модуля>/`, как делают штатные модули. Делается это в
`DoInstall()`, снимается в `DoUninstall()`:

```php
CopyDirFiles(__DIR__ . '/../js', $_SERVER['DOCUMENT_ROOT'] . '/bitrix/js/shef.leadfinish/js', true, true);
// ...
DeleteDirFilesEx('/bitrix/js/shef.leadfinish');
```

Побочный итог полезный: путь к фронту перестаёт зависеть от места установки
модуля.

```bash
cd /home/bitrix/www/bitrix/modules/
unzip -o shef.leadfinish.zip
chown -R bitrix:bitrix shef.leadfinish
```

Дальше — админка: **Marketplace → Установленные решения** (или
`/bitrix/admin/partner_modules.php`) → «Установить» у нужного модуля.

## Настройки, которые живут в файле

Модуль может хранить настройки не в базе, а в `.settings.php` — тогда порядок
шагов перестаёт быть безразличным, потому что **раскладка файлов этот файл
перетирает**: и `unzip -o`, и `composer update` одинаково. Заполнять его нужно
строго **после** раскладки:

```bash
cd /home/bitrix/www/bitrix/modules/
unzip -o shef.leadfinish.zip        # 1. файлы, .settings.php — ПОСТАВОЧНЫЙ
vim shef.leadfinish/.settings.php   # 2. и только теперь — свои значения
chown -R bitrix:bitrix shef.leadfinish
```

Поставочные значения — это не «пусто», а рабочая настройка, обычно самая узкая:
в `shef.leadfinish` там `allowed_users => [1]`, то есть один администратор
портала. Пропустить второй шаг — значит поставить модуль, которого никто не
видит, и дальше искать ошибку в коде, которой там нет.

На обновлении та же связка разворачивается наоборот: значения, выставленные на
сервере, обновление молча вернёт к поставочным, и заметить это можно будет
только по пропавшей кнопке. Надёжный способ один — держать нужные значения **в
самой поставке**, в репозитории, откуда собираются и архив, и Composer-пакет:
тогда обновление приезжает уже настроенным и возвращать нечего. Правятся они
только на сервере — выписать перед обновлением (`cat .settings.php`) и вернуть
после.

Обновление уже стоящего модуля: разложить файлы поверх, вернуть настройки и
**переустановить** через админку, если менялись установочные события. Если
менялись только `lib/`, `js/`, `css/` — достаточно раскладки.

## После установки

**Сбросить кеш JS/CSS.** Битрикс отдаёт склеенные файлы из
`/bitrix/cache/js/s1/...`, и правка фронта до браузера не доедет. Либо Ctrl+F5,
либо админка → «Настройки продукта» → «Автокеширование» → сбросить.

Путь вида `/bitrix/cache/js/s1/...` в консоли браузера — верный признак, что
смотришь на кеш, а не на свой файл.

**Проверить, что версия совпадает** с той, что собирал: список установленных
решений её показывает.

## Приёмочный сценарий

Держать в `CLAUDE.md` модуля список обязательных проверок и проходить его после
каждой сборки. Автотестов у такого кода обычно нет — логика завязана на рантайм
Битрикса, — поэтому чек-лист и есть тест.

Пример из `shef.leadfinish`:

1. кнопка подменилась, штатная красная на месте;
2. подбор находит сделку по части номера;
3. «Открыть ↗» открывает сделку в новой вкладке и не сбивает подбор;
4. после «Выбрать» закрылись **оба** окна и открылся слайдер;
5. данные проставились в обеих сущностях, в обоих таймлайнах записи;
6. под пользователем **не** из белого списка кнопки нет, **и** прямой вызов
   ajax-действия возвращает ошибку доступа.

Пункт 6 — не формальность. Кнопку спрятать мало: адрес действия известен из кода
модуля и вызывается напрямую. Права проверяются и на показ, и в контроллере.
