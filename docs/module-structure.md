# Структура локального модуля Битрикс24

Опыт `shef.leadfinish`. Модуль **переносимый**: ставится на любой портал в
`/local/modules/`, не зависит от кастома конкретного клиента.

## Именование

`shef.<name>` — точка обязательна, это разделитель «вендор.модуль» в Битриксе.
Из него выводится всё остальное, и расхождения не прощаются:

| Что | Правило | Пример |
| --- | --- | --- |
| ID модуля | `shef.leadfinish` | — |
| Класс установки | точка → подчёркивание | `class shef_leadfinish extends CModule` |
| Namespace | CamelCase по частям | `Shef\LeadFinish` |
| Вызов ajax с фронта | точка → двоеточие | `shef:leadfinish.DealBinder.bind` |
| Каталог | = ID модуля | `/local/modules/shef.leadfinish/` |

## Раскладка файлов

```
shef.leadfinish/
├── install/
│   ├── index.php          класс CModule: DoInstall / DoUninstall, события
│   └── version.php        $arModuleVersion — VERSION, VERSION_DATE
├── lang/ru/
│   └── install/index.php  название модуля, описание, имя партнёра
├── lib/                   классы, автозагрузка по namespace
│   ├── access.php         Shef\LeadFinish\Access
│   └── controller/
│       └── dealbinder.php Shef\LeadFinish\Controller\DealBinder
├── js/
├── css/
├── include.php            Loader::registerNamespace('Shef\LeadFinish', lib/)
├── options.php            страница настроек в админке — если она нужна
├── .settings.php          ajax-контроллеры + конфигурация модуля
├── composer.json          если модуль ставится и через Composer
├── README.md              описание процесса для человека
└── CLAUDE.md              памятка для AI-агента: почему сделано так
```

### Где это лежит в репозитории

Каталог выше — то, что уезжает на портал. В репозитории он может лежать
двумя способами, и выбор не косметический:

| Раскладка | Когда | Цена |
| --- | --- | --- |
| модуль в подкаталоге `shef.leadfinish/` | ставим только архивом | наглядно: код модуля отделён от сборки и тестов |
| **модуль в корне репозитория** | ставим ещё и через Composer | Composer разворачивает корень пакета целиком и подкаталоги выбирать не умеет |

`shef.leadfinish` перешёл на вторую: файлы модуля в корне, а `tests/`, `docs/`,
`build.sh`, `CONTRIBUTING.md`, `.github/` отсекаются от поставки через
`export-ignore` в `.gitattributes` и списком `KEEP` в `build.sh`.

⚠ Тогда архив приходится **собирать**, а не архивировать готовый каталог: первым
уровнем в zip обязан быть `shef.leadfinish/`, а в репозитории такого каталога
больше нет. Подробности — в `build-and-install.md`.

⚠ И следи, чтобы два списка не разъехались: `export-ignore` решает, что попадёт
в Composer-пакет, `KEEP` — что попадёт в архив. Разойдутся — на портал уедет
разное в зависимости от способа установки, и разбираться в этом будешь не сразу.

### Правила, на которых легко обжечься

**Имена файлов в `lib/` строго в нижнем регистре.** Автозагрузка идёт через
`Loader::registerNamespace`, который переводит имя класса в путь в нижнем
регистре. `Shef\LeadFinish\Controller\DealBinder` → `lib/controller/dealbinder.php`.
Файл `DealBinder.php` не найдётся — но только на Linux, локально под Windows
всё «работает».

**Настройки — два разных механизма, не путать.**

- `Option::get/set($moduleId, $key)` — настройки **в базе**, правятся через
  `options.php` в админке. Для того, что меняет пользователь портала.
- `.settings.php` + `Configuration::getInstance($moduleId)->get($key)` —
  настройки **в файле**. Для того, что правит разработчик или заказчик прямо на
  сервере: расписания, рубильники, режимы. Файл виден в репозитории и в поставке,
  правка — секунды, без переустановки модуля.

**`.settings.php` обязателен, если есть ajax:**

```php
'controllers' => [
	'value' => ['defaultNamespace' => '\\Shef\\LeadFinish\\Controller'],
	'readonly' => true,
],
```

Без этого блока действия контроллера просто не находятся, и ошибка выглядит как
«метод не существует».

**`DoInstall()` не должен затирать ручные настройки.** Переустановка модуля —
штатная операция при обновлении. Значение по умолчанию ставим только если
настройки ещё нет:

```php
if (Option::get($this->MODULE_ID, 'report_email', '') === '')
{
	Option::set($this->MODULE_ID, 'report_email', self::DEFAULT_REPORT_EMAIL);
}
```

Обратная сторона: настройка в файле переустановку переживает, а **распаковку
архива поверх — нет**. Что правит заказчик на сервере, должно лежать и в
репозитории, иначе следующая поставка вернёт прежнее значение.

**Одну настройку — одним механизмом.** Держать её и в базе, и в файле «на всякий
случай» нельзя: два источника одной правды рано или поздно разойдутся, и никто
не скажет, какой из них действует. Если настройка уехала в файл — страницу в
админке надо убирать, а не оставлять «просто посмотреть».

**`DoUninstall()` обязан убирать за собой** — `UnRegisterModule`,
`UnInstallEvents`. Модуль, который не удаляется чисто, нельзя переставить.

**Проверка `class_exists` в начале `install/index.php`.** Файл включается
несколько раз за запрос — без неё будет фатальная ошибка повторного объявления.

## Два описания вместо одного

Опыт показал, что `README.md` и `CLAUDE.md` — разные документы и объединять их
не надо.

- **`README.md`** — для человека: что модуль делает, как это выглядит для
  пользователя, как поставить и настроить. Без внутренностей.
- **`CLAUDE.md`** — для AI-агента: то, чего не видно из кода. Опорные точки в
  чужом коде, ловушки, на которых уже обожглись, и решения владельца, которые
  **не надо переигрывать** («сделку с чужим лидом выбрать можно, связь
  перезаписывается» — иначе следующий агент «починит» это как баг).

## Ядро не правим

Ни одного файла в `bitrix/`. Вся интеграция — через публичные события ядра и
универсальное API. Если задача выглядит так, будто нужна правка ядра, — это
сигнал искать событие или точку расширения, а не повод патчить поставку: правка
будет затёрта ближайшим обновлением платформы.

Завязки на чужой код документируются таблицей в `CLAUDE.md`: что ловим, где оно
формируется в ядре, как ловим. Это список того, что проверяется при обновлении
платформы.

По возможности цепляться за **суффиксы** id, а не за целые строки: переименование
контрола в ядре тогда ничего не ломает.
