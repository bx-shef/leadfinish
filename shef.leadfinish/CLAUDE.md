# Модуль `shef.leadfinish` — памятка для AI-агента

Читай это до правок. Здесь то, что не видно из кода: почему сделано именно так и
на чём легко обжечься.

Пользовательское описание процесса — в `README.md`. Дублировать его здесь не надо.

Разработчик — ИП Шевчик И.С., [bx-shef.by](https://bx-shef.by/).

## Что это

Локальный модуль Битрикс24. Подменяет зелёную кнопку «Создать на основании: …» в
попапе завершения обработки лида на свою «Подобрать сделку»: менеджер связывает
лид с **уже существующей** сделкой вместо создания новой.

Модуль **переносимый и самодостаточный**: ставится в `/local/modules/`, не зависит
от кастома конкретного портала.

## Железные правила

**Ядро Битрикса не правим.** Ни одного файла в `bitrix/` модуль не меняет и не
должен. Вся интеграция — через публичные события и универсальное API CRM. Если
задача выглядит так, будто нужна правка ядра, — ищи событие или точку расширения.

**Общаемся и пишем комментарии по-русски.** Код в стиле Битрикса: табы,
аллмановские скобки, `BX.create()` на фронте.

**Права проверяем всегда.** И на показ кнопки, и в ajax-действиях. Кнопку спрятать
мало: адрес действия известен и вызывается напрямую.

## Опорные точки в ядре

Тут завязки на чужой код — самое хрупкое место модуля. Первые три проверяются в
`bitrix/js/crm/progress_control.js`.

| Что | Где формируется | Как ловим |
| --- | --- | --- |
| Попап завершения лида | `BX.CrmProgressControl`, `id = ${controlId}_TERMINATION` | подписка на `BX.Main.Popup:onAfterShow`, фильтр по **суффиксу** id |
| Обёртка зелёной кнопки | `BX.CrmLeadTerminationControl.prepareDialogControls`, `id = (${controlId}_success_btn_wrapper).toLowerCase()` | `querySelector('[id$="_success_btn_wrapper"]')` |
| Событие показа попапа | `PopupWindow` объявляет namespace `BX.Main.Popup` и эмитит `onAfterShow` | `BX.Event.EventEmitter.subscribe` |
| ID лида | `CCrmViewHelper::RenderProgressControl()`, `controlId = "{ПРЕФИКС}{ТИП}_{id}"` | `getLeadId()`, разбор `_LEAD_(\d+)_TERMINATION` |
| ID грида списка | `crm.lead.list/templates/.default/template.php`, `PREFIX = "{GRID_ID}_PROGRESS_BAR_"` | `reloadGrid()`, разбор префикса из id попапа |

Канбан — в `crm.kanban/templates/.default/script.js`:

| Что | Где формируется | Как ловим |
| --- | --- | --- |
| Окно выбора | `showPopup()`, `new BX.PopupWindow("kanban_column_popup", …)` | точный id + контейнер `crm_kanban_lead_win` внутри |
| Карточка лида | `showPopup()`, `currentPopupItem = handlerData.item` до показа окна | `getKanbanLeadId()` |
| Возврат карточки | `onPopupClose` → `returnItem()`, если `successClosePopup !== true` | флаг выставляем в `closeAll()` |
| Обновление доски | `BX.CRM.Kanban.Grid::reload()` | `reloadKanban()` |

Завязки на прогресс-бар сделаны на **суффиксы** id намеренно: переименование
самого контрола (`entity_progress` и т.п.) ничего не ломает. В канбане id, наоборот,
точный — он захардкожен в ядре.

При обновлении платформы проверять все эти пункты.

## Ловушки, на которых уже обжигались

**Оригинальную кнопку нельзя удалять — только прятать.** На открытии попапа ядро
вешает на её внутренности селектор схем конверсии
(`BX.CrmLeadConversionSchemeSelector`), а на закрытии дёргает его `release()`.
Удаление узла оставит селектор со ссылками на несуществующий DOM.

**Попапы закрывать только через объекты**, не `display:none` по селектору.
Спрятанный стилями попап продолжает считать себя открытым и ломает следующее
открытие. Объект попапа завершения приходит в контекст — используй его.

**`CCrmCurrency::MoneyToString()` возвращает HTML-сущности.** Он делает
`strip_tags`, но `&nbsp;` остаётся. Фронт рисует текстом — сущность вылезает как
есть. Раскрывать на сервере (`html_entity_decode` + замена U+00A0), см.
`DealSearch::formatMoney()`.

**Кеш JS/CSS.** После правок фронта нужен Ctrl+F5 или сброс автокеширования в
админке. Путь вида `/bitrix/cache/js/s1/...` в консоли — верный признак, что
смотришь на кеш, а не на свой файл.

**`*.min.js` рядом с правленым файлом.** При включённой оптимизации Битрикс
отдаст минифицированную версию, и правка до браузера не доедет. У модуля своих
`min`-файлов нет — не заводи.

### Доступ

`Access::isAllowedUser()` — один метод и для показа кнопки, и для ajax. Список
живёт в `.settings.php`, ключ `allowed_users`: массив ID или строка через запятую.

**Пустой список = всем авторизованным.** Это осознанное решение владельца: после
обкатки включить на всех, просто очистив список. Не «чини» это на «пусто =
никому».

**Отсутствие ключа — не то же самое, что пустой список:** тогда **никому**. Ключа
обычно нет из-за неполного обновления (распаковали `lib/`, а `.settings.php`
остался старый), и «пусто = всем» в этом случае молча раскатало бы кнопку на
портал. Различить их можно только ДО разбора списка, поэтому проверка на `null`
стоит первой — не переставляй.

Мусор (`abc`) даёт пустой список ID — и тогда тоже **никому**, а не всем.
Опечатка в настройке не должна расширять доступ.

Матрица целиком закрыта тестом `tests/access_test.php`: ядро там подменено
заглушками, поэтому проверяется настоящий класс. Меняешь правила — правь тест
в том же PR.

Страницы настроек в админке нет намеренно, и заводить её обратно не надо: файл
и база — два источника одной правды, которые однажды разойдутся.

**В поставке стоит `[1]` — один администратор портала.** Поэтому запуск на
портале без правки `.settings.php` даёт модуль, которого никто не видит: это не
баг, а пропущенный шаг установки. Порядок шагов расписан в README модуля,
раздел «Установка», и порядок там существенный — список правится **после**
распаковки, потому что `unzip -o` этот файл перетирает. Меняешь правила
доступа — проверь, что README всё ещё описывает их верно.

### Серверная логика

Только универсальное API CRM: `Service\Container` → `Factory` → `Operation` с
`enableCheckAccess()`. Прямые запросы к базе и legacy `CCrmDeal::Update()` не
использовать — операции сами делают нормализацию, историю, индексацию и права.

Подбор — `Factory::getItemsFilteredByPermissions()`. Это единственный правильный
способ списка: он подмешивает ограничения прав в сам запрос.

**Порядок в `Binder::bind()` менять нельзя:** сначала связь в сделку, потом
закрытие лида. Если упадёт второй шаг, останется привязанная сделка при открытом
лиде — это видно и чинится повторным нажатием. Обратный порядок даст закрытый лид
без связи, что заметить куда труднее.

Таймлайн — вспомогательная запись. Его ошибка **не должна** ронять уже
выполненную привязку; она уходит в `AddMessage2Log`.

Привязка комментария к сущности задаётся **только через `BINDINGS`** —
`ENTITY_TYPE_ID`/`ENTITY_ID` на верхнем уровне `CommentEntry::create()`
игнорируются (см. `TimelineEntry::fetchParams()`).

### Фронт

JS подключается **узко**: только на страницах, где попап завершения вообще есть,
и только пользователям из списка. Он вешает глобальный слушатель попапов — на
остальных страницах портала это лишнее. Список страниц — один, в
`EventHandler::matchesLeadPath()`, и закрыт тестом `tests/eventhandler_test.php`.

Сейчас это **карточка лида и список лидов**. Попап там один и тот же, ядро
строит его в обоих местах через `CCrmViewHelper::RenderProgressControl()`.

**Канбан — второй механизм, не тот же самый.** Окно там своё,
`kanban_column_popup`, открывается перетаскиванием карточки в колонку «сделка».
Три отличия, каждое способно тихо сломать:

- **id окна общий.** Под `kanban_column_popup` ядро показывает и счета.
  Отличаем по содержимому — контейнер `crm_kanban_lead_win` бывает только у
  лида. Фильтровать по одному id нельзя.
- **Лид берётся из состояния компонента**, не из DOM и не из адреса:
  `BX.Crm.KanbanComponent.currentPopupItem` выставляется ДО показа окна.
- **`successClosePopup` обязателен перед закрытием.** Карточка на время окна
  спрятана (или её ход не зафиксирован), и на закрытии компонент возвращает её
  в исходную колонку. Забыть флаг — привязка выполнена, а доска показывает,
  будто ничего не было. Ровно это делает и штатный `leadConvert()`.
- **Содержимое окна не пересоздаётся.** `setContent(BX('crm_kanban_lead_win'))`
  подставляет один и тот же статический узел. Отсюда два следствия, и оба
  кусаются со второго открытия: наш пункт остаётся в DOM вместе с замыканием на
  **прошлый лид**, а `showPopup()` заново расставляет вариантам `display`, и
  окно снова выглядит штатным. Поэтому в канбане пункт **удаляем и вставляем
  заново**, а варианты прячем **на каждом** открытии — проверка «маркер уже
  есть, выходим» тут неприменима.

  В карточке и списке ровно наоборот: `prepareDialogControls()` строит кнопки
  через `BX.create()` при каждом открытии, там пересоздавать нечего.

После привязки доску перечитываем целиком (`currentData.grid.reload()`):
двигать карточку руками смысла нет, лид всё равно закрыт и уходит с доски.

**ID лида берём из id попапа, а не из адреса.** `getLeadId()` сперва читает
`_LEAD_{id}_TERMINATION`, и только если не вышло — разбирает `location.pathname`.
Порядок важен: в списке в адресе никакого id нет, а на карточке прогресс-бар
рисует редактор сущности, и формат его id может отличаться от списочного.
Запасной путь по адресу как раз и страхует карточку.

**После привязки из списка таблицу надо перечитать** — `reloadGrid()`. Иначе
строка остаётся в прежней стадии до перезагрузки страницы, и выглядит это как
«не сработало». ID грида выводится из того же id попапа: шаблон списка задаёт
прогресс-бару префикс `{GRID_ID}_PROGRESS_BAR_`. В карточке вызов ничего не
находит и тихо выходит — так и задумано.

`window.shefLeadFinishConfig` — параметры с сервера (минимальная длина запроса,
период поиска). Не хардкодить их в JS: значения живут в `DealSearch`.

`var DEBUG` вверху файла — по умолчанию `false`. Включать только на время отладки.

## Приостановка доработки (`lib/lock.php`)

Механика «приём работ не оформлен»: `soft` — напоминание с отсчётом, `hard` —
подбор не открывается. Перенесена по образцу `bx-shef/some-report`, PR #72.

Инварианты, которые нельзя трогать:

- **Дат в коде нет.** Расписание живёт в `.settings.php`, раздел `lock`. Файл
  видит заказчик, и «заблокировать их 17-го» в коде — плохой способ вести
  разговор о приёмке. Плюс снимать приостановку нужно правкой одного файла.
- **Ошибка в настройках уводит к РАБОТАЮЩЕЙ доработке.** Негодная дата
  отбрасывается, мусор в `off` не выключатель, мусор в `users` не означает
  «всем». Запереть оформившего из-за своей опечатки хуже, чем не напомнить.
  Про `users` это держится на том, что `UserList::parse()` разводит «списка нет
  или он пуст» (`null`, значит всех) и «список задан, но нечитаем» (пустой
  массив, значит никого). До 1.4.1 оба случая давали один пустой массив, и опечатка
  запирала портал. Не склеивай их обратно — матрица закрыта
  `tests/lock_test.php`.
- **Жёсткая дата проверяется первой** — чтобы перепутанные местами даты давали
  «жёстко с более ранней», а не тихую бессмыслицу.
- **Обход `?lock=` только повышает ступень.** `?lock=none` не заводить никогда:
  такая ссылка разойдётся по переписке за минуту.
- **Рубильник `off` и «не про этого пользователя» гасят обход.** Обе проверки
  стоят в `currentStage()` ДО него и выходят сразу — не переставляй. Пропустишь
  обход вперёд — и `?lock=hard` вернёт экран приостановки после оформленной
  приёмки, причём контроллер в этот момент действие разрешает (он зовёт
  `currentStage()` без обхода), то есть фронт и сервер разойдутся.
- **Сервер решает, фронт рисует.** `hard` запрещается в контроллере, иначе
  приостановка снимается правкой JS в консоли.
- **На `hard` штатная кнопка ядра остаётся видимой.** Приостанавливается наша
  доработка, а не CRM заказчика: спрятав кнопку ядра и заблокировав свою, мы
  отняли бы у менеджера возможность завершить лид вообще.
- **Формулировки нейтральные.** Экран видит рядовой менеджер. Ни слова о
  деньгах, долге и чьей-либо вине — только о формальности между организациями.
- **Анимация отключается по `prefers-reduced-motion`**, и рисунок без движения
  остаётся осмысленным.
- **Высота экрана в пикселях, не в `vh`.** Карточка лида часто открыта в
  слайдере: `vh` внутри фрейма схлопывает экран в полоску.

## Решения владельца — не переигрывать

- Сделку, уже привязанную к другому лиду, **выбрать можно**, прежняя связь
  **перезаписывается**.
- Лид закрывается **независимо от текущего статуса**: повторное закрытие уже
  закрытого лида — нормально.
- Ищем **только по названию** сделки (`TITLE`), не по ID и не по номеру счёта.
- Период поиска — **7 дней**, любая стадия, любая воронка.
- Проверки прав и автоматизация при обновлении сделки **включены** — операция
  выполняется так, как если бы поле изменил человек.

## Проверка

Почти всё завязано на рантайм Битрикса, поэтому основная проверка ручная,
сценарий — в `README.md`, раздел «Как это выглядит для менеджера».

Исключение — чистая логика, которую видно без портала: она покрыта тестами в
`tests/` репозитория и гоняется в CI (`./build.sh --check`). Сейчас это
`tests/access_test.php` (кому доступна кастомизация), `tests/lock_test.php`
(кого касается приостановка, ступень на день, обход из адреса) и
`tests/eventhandler_test.php` (на каких страницах подключаются ассеты).
Добавляешь такую логику — добавляй и тест, чек-лист ниже её не ловит.

Обязательный минимум после правок:

1. кнопка подменилась, красная «Забраковать» на месте;
2. подбор находит сделку по части номера;
3. «Открыть ↗» открывает сделку в новой вкладке и **не** сбивает подбор;
4. после «Выбрать» закрылись **оба** окна и открылся слайдер;
5. в сделке проставился `LEAD_ID`, лид в `CONVERTED`, в обоих таймлайнах записи;
6. под пользователем **не** из списка кнопки нет, а прямой вызов
   `shef:leadfinish.DealBinder.bind` возвращает ошибку доступа;
7. то же самое из **списка лидов** (`/crm/lead/list/`): кнопка в строке
   подменилась, подбор привязал сделку — и **строка сразу показала новую
   стадию**, без перезагрузки страницы;
8. в списке открыть попап у **разных** лидов подряд: каждый должен привязывать
   свой лид, а не тот, что открывали первым;
9. в **канбане** перетащить карточку лида в колонку «Сделка»: в окне вместо
   списка вариантов конвертации — один пункт «Подобрать сделку»;
10. после привязки из канбана доска перечиталась, лид с неё ушёл — и **карточка
    не вернулась** в исходную колонку;
11. закрыть окно канбана крестиком или «Отмена», ничего не выбрав: карточка
    **вернулась** на место, лид не тронут;
11а. ⚠ перетащить **второй раз подряд**, и лучше другой лид: окно снова
    показывает только наш пункт (а не штатные варианты), и привязывается
    именно этот лид, а не предыдущий. Узел окна переиспользуется, и это первое,
    что здесь ломается;
12. перетащить в колонку «Сделка» **счёт** (если канбан счетов используется):
    штатное окно счёта открылось без нашего пункта.

Перед сдачей — `./build.sh --check` из корня репозитория: `php -l`, `node --check`,
регистр имён в `lib/` и тесты.

## Версионирование

`install/version.php`. Поднимать при каждом изменении поведения; в `README.md`
держать описание в актуальном виде.
