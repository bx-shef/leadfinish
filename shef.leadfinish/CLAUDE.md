# Модуль `shef.leadfinish` — памятка для AI-агента

Читай это до правок. Здесь то, что не видно из кода: почему сделано именно так и
на чём легко обжечься.

Пользовательское описание процесса — в `README.md`. Дублировать его здесь не надо.

Разработчик — ИП Шевчик И.С., [bx-shef.by](http://bx-shef.by/).

## Что это

Локальный модуль Битрикс24. Подменяет зелёную кнопку «Создать на основании: …» в
попапе завершения обработки лида на свою «Подобрать сделку»: менеджер связывает
лид с **уже существующей** сделкой вместо создания новой.

Модуль **переносимый и самодостаточный**: ставится в `/local/modules/`, не зависит
от кастома конкретного портала.

## Железные правила

**Ядро Битрикса не правим.** Ни одного файла в `bitrix/` модуль не меняет и не
должен. Вся интеграция — через публичные события и универсальное API CRM. Если
задача выглядит так, будто нужна правка ядра, — ищи событие или точку расширения.

**Общаемся и пишем комментарии по-русски.** Код в стиле Битрикса: табы,
аллмановские скобки, `BX.create()` на фронте.

**Права проверяем всегда.** И на показ кнопки, и в ajax-действиях. Кнопку спрятать
мало: адрес действия известен и вызывается напрямую.

## Опорные точки в ядре

Тут завязки на чужой код — самое хрупкое место модуля. Все три проверяются в
`bitrix/js/crm/progress_control.js`.

| Что | Где формируется | Как ловим |
| --- | --- | --- |
| Попап завершения лида | `BX.CrmProgressControl`, `id = ${controlId}_TERMINATION` | подписка на `BX.Main.Popup:onAfterShow`, фильтр по **суффиксу** id |
| Обёртка зелёной кнопки | `BX.CrmLeadTerminationControl.prepareDialogControls`, `id = (${controlId}_success_btn_wrapper).toLowerCase()` | `querySelector('[id$="_success_btn_wrapper"]')` |
| Событие показа попапа | `PopupWindow` объявляет namespace `BX.Main.Popup` и эмитит `onAfterShow` | `BX.Event.EventEmitter.subscribe` |

Завязки сделаны на **суффиксы** id намеренно: переименование самого контрола
(`entity_progress` и т.п.) ничего не ломает.

При обновлении платформы проверять именно эти три пункта.

## Ловушки, на которых уже обжигались

**Оригинальную кнопку нельзя удалять — только прятать.** На открытии попапа ядро
вешает на её внутренности селектор схем конверсии
(`BX.CrmLeadConversionSchemeSelector`), а на закрытии дёргает его `release()`.
Удаление узла оставит селектор со ссылками на несуществующий DOM.

**Попапы закрывать только через объекты**, не `display:none` по селектору.
Спрятанный стилями попап продолжает считать себя открытым и ломает следующее
открытие. Объект попапа завершения приходит в контекст — используй его.

**`CCrmCurrency::MoneyToString()` возвращает HTML-сущности.** Он делает
`strip_tags`, но `&nbsp;` остаётся. Фронт рисует текстом — сущность вылезает как
есть. Раскрывать на сервере (`html_entity_decode` + замена U+00A0), см.
`DealSearch::formatMoney()`.

**Кеш JS/CSS.** После правок фронта нужен Ctrl+F5 или сброс автокеширования в
админке. Путь вида `/bitrix/cache/js/s1/...` в консоли — верный признак, что
смотришь на кеш, а не на свой файл.

**`*.min.js` рядом с правленым файлом.** При включённой оптимизации Битрикс
отдаст минифицированную версию, и правка до браузера не доедет. У модуля своих
`min`-файлов нет — не заводи.

## Архитектура

```
install/index.php        установка/удаление, регистрация main::OnEpilog
options.php              страница настроек в админке
.settings.php            объявление ajax-контроллеров
include.php              Loader::registerNamespace('Shef\LeadFinish', lib/)

lib/access.php           кому доступна кастомизация — ЕДИНЫЙ источник правды
lib/lock.php             ступень приостановки (расписание из .settings.php)
lib/eventhandler.php     подключение JS/CSS на детальной лида
lib/dealsearch.php       подбор сделок с учётом прав
lib/binder.php           привязка сделки, закрытие лида, таймлайны
lib/controller/dealbinder.php   ajax: search / bind

js/lead-finish-button.js подмена кнопки + окно подбора
css/lead-finish.css      оформление подбора
```

Автозагрузка — через `registerNamespace`, поэтому **имена файлов в `lib/` строго в
нижнем регистре**: `Shef\LeadFinish\Controller\DealBinder` → `lib/controller/dealbinder.php`.

### Доступ

`Access::isAllowedUser()` — один метод и для показа кнопки, и для ajax. Настройка
`allowed_users` (ID через запятую).

**Пустое значение = всем авторизованным.** Это осознанное решение владельца:
после обкатки включить на всех, просто очистив поле. Не «чини» это на «пусто =
никому».

Мусор в поле (`abc`) даёт пустой список ID — и тогда **никому**, а не всем.
Опечатка в настройке не должна тихо раскатывать функциональность на портал.

### Серверная логика

Только универсальное API CRM: `Service\Container` → `Factory` → `Operation` с
`enableCheckAccess()`. Прямые запросы к базе и legacy `CCrmDeal::Update()` не
использовать — операции сами делают нормализацию, историю, индексацию и права.

Подбор — `Factory::getItemsFilteredByPermissions()`. Это единственный правильный
способ списка: он подмешивает ограничения прав в сам запрос.

**Порядок в `Binder::bind()` менять нельзя:** сначала связь в сделку, потом
закрытие лида. Если упадёт второй шаг, останется привязанная сделка при открытом
лиде — это видно и чинится повторным нажатием. Обратный порядок даст закрытый лид
без связи, что заметить куда труднее.

Таймлайн — вспомогательная запись. Его ошибка **не должна** ронять уже
выполненную привязку; она уходит в `AddMessage2Log`.

Привязка комментария к сущности задаётся **только через `BINDINGS`** —
`ENTITY_TYPE_ID`/`ENTITY_ID` на верхнем уровне `CommentEntry::create()`
игнорируются (см. `TimelineEntry::fetchParams()`).

### Фронт

JS подключается **узко**: только на детальной лида и только пользователям из
списка. Он вешает глобальный слушатель попапов — на остальных страницах портала
это лишнее.

`window.shefLeadFinishConfig` — параметры с сервера (минимальная длина запроса,
период поиска). Не хардкодить их в JS: значения живут в `DealSearch`.

`var DEBUG` вверху файла — по умолчанию `false`. Включать только на время отладки.

## Приостановка доработки (`lib/lock.php`)

Механика «приём работ не оформлен»: `soft` — напоминание с отсчётом, `hard` —
подбор не открывается. Перенесена по образцу `bx-shef/some-report`, PR #72.

Инварианты, которые нельзя трогать:

- **Дат в коде нет.** Расписание живёт в `.settings.php`, раздел `lock`. Файл
  видит заказчик, и «заблокировать их 17-го» в коде — плохой способ вести
  разговор о приёмке. Плюс снимать приостановку нужно правкой одного файла.
- **Ошибка в настройках уводит к РАБОТАЮЩЕЙ доработке.** Негодная дата
  отбрасывается, мусор в `off` не выключатель, мусор в `users` не означает
  «всем». Запереть оформившего из-за своей опечатки хуже, чем не напомнить.
- **Жёсткая дата проверяется первой** — чтобы перепутанные местами даты давали
  «жёстко с более ранней», а не тихую бессмыслицу.
- **Обход `?lock=` только повышает ступень.** `?lock=none` не заводить никогда:
  такая ссылка разойдётся по переписке за минуту.
- **Сервер решает, фронт рисует.** `hard` запрещается в контроллере, иначе
  приостановка снимается правкой JS в консоли.
- **На `hard` штатная кнопка ядра остаётся видимой.** Приостанавливается наша
  доработка, а не CRM заказчика: спрятав кнопку ядра и заблокировав свою, мы
  отняли бы у менеджера возможность завершить лид вообще.
- **Формулировки нейтральные.** Экран видит рядовой менеджер. Ни слова о
  деньгах, долге и чьей-либо вине — только о формальности между организациями.
- **Анимация отключается по `prefers-reduced-motion`**, и рисунок без движения
  остаётся осмысленным.
- **Высота экрана в пикселях, не в `vh`.** Карточка лида часто открыта в
  слайдере: `vh` внутри фрейма схлопывает экран в полоску.

## Решения владельца — не переигрывать

- Сделку, уже привязанную к другому лиду, **выбрать можно**, прежняя связь
  **перезаписывается**.
- Лид закрывается **независимо от текущего статуса**: повторное закрытие уже
  закрытого лида — нормально.
- Ищем **только по названию** сделки (`TITLE`), не по ID и не по номеру счёта.
- Период поиска — **7 дней**, любая стадия, любая воронка.
- Проверки прав и автоматизация при обновлении сделки **включены** — операция
  выполняется так, как если бы поле изменил человек.

## Проверка

Автотестов нет: логика завязана на рантайм Битрикса. Проверка ручная, сценарий —
в `README.md`, раздел «Как это выглядит для менеджера».

Обязательный минимум после правок:

1. кнопка подменилась, красная «Забраковать» на месте;
2. подбор находит сделку по части номера;
3. «Открыть ↗» открывает сделку в новой вкладке и **не** сбивает подбор;
4. после «Выбрать» закрылись **оба** окна и открылся слайдер;
5. в сделке проставился `LEAD_ID`, лид в `CONVERTED`, в обоих таймлайнах записи;
6. под пользователем **не** из списка кнопки нет, а прямой вызов
   `shef:leadfinish.DealBinder.bind` возвращает ошибку доступа.

Синтаксис перед сдачей: `php -l` по всем PHP и `node --check` по JS.
